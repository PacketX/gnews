# 64 bytes 封包的每秒轉送量(pps)

最小封包下,一台設備每秒能**不漏任何一個封包**地轉送多少個?本頁是 G8S、T12S、Q16、HL1 四個機型在「開 flow 表(出廠預設)」與「關 flow 表(最佳化)」兩種設定下量到的結果(2026-11-06、11-09 與 11-16;G8S、T12S 韌體 6.6.261104,Q16 7.6.261106(11-16 重測 7.6.261116),HL1 7.6.261116)。每秒封包數是小封包流量的瓶頸:同樣的 pps,封包越大吞吐量越高,所以把 64 bytes 的 pps 乘上實際流量的平均封包大小,就是該設備在那種流量下的上限(例如 0.92 Mpps × 600 bytes ≈ 4.4 Gbit/s)。

## 測試方式

- **被測設備不自己產生流量。** 流量由另一台 GRISM 的 traffic-gen 輸入送出,經實體線進入被測設備;被測設備用一條鏈(一個 `ip.src == 11.0.0.0/8` 過濾器,全部命中)轉送到另一個埠,再接回產生流量的那台計數。沒有用 LOOP 埠。
- **封包**:UDP,`packet_size` 60,線上含 FCS 剛好 64 bytes(traffic-gen 的 `packet_size` 不含 FCS,填 64 會變成 68 bytes 的封包)。每個產生器以一段連續的來源位址輪流送(`src_ip_min` / `src_ip_max` / `src_ip_inc`),所以每個封包都是不同的 flow。
- **flow 數**:開 flow 表的測試讓所有產生器的來源位址總數約等於 flow 表容量(`flowCacheBaseSize × 16`,ARM64 系列再 × 工作核心數)的 **75%**:G8S 48 萬、T12S 180 萬、Q16 635 萬、HL1 193 萬。太少不行——單一 flow 在 OCTEON 上會被 atomic tag 綁在一顆核心,量到的是一顆核心而不是整台(G8S 單一 flow 只有 0.49 Mpps),flow 數只有幾萬時表幾乎是空的、數字會偏高;太滿也不行,接近滿的表會把數字再壓低(見結果後的說明)。關 flow 表的測試 flow 數無關緊要。
- **速率**:第一輪不限速(灌到線速或產生器的上限),掉包就以 traffic-gen 的 `speed` 二分,每輪暖機 15 秒、取 60 秒視窗,共 7 輪(解析度約 1%)。
- **通過**:60 秒內被測設備**所有埠**的 `inDrops`、`inErrors`、`outDrops` 都是 0(Q16 的 NIC 丟包記在引擎的上行埠 P0–P2,不在 V 埠),而且被測設備出 = 進(容許 0.1 秒流量的差:進是硬體計數、出是各核心的軟體計數加總,不是同一瞬間讀的)。產生器那台收到的(inPackets + inDrops,因為它自己的引擎吃不下回流時會丟在進埠)與送出的差只當作超過 1% 才成立的防呆,防的是沒有人計數的漏失(交換器、線)。**HL1 例外**:它接近上限時的漏失不會出現在任何 drop 計數器(見結果後的說明),所以改看實際少了多少——收進但沒送出、也沒記成 drop 的封包,以及產生器那端的送收差——兩者超過約 5 毫秒的流量(60 秒內約 1.5 至 2 萬個)就算掉包。
- **開 flow**(出廠預設)= 用「回復原廠設定(保留管理 IP)」還原後的設定,不改任何東西(MEC 機型的 MEC 功能為開)。**關 flow**(最佳化)= 關閉 flow / flowv6 表、L7 解析、tunnel 內層解析、SCTP / TCP / QUIC 重組、IP 分片關聯、去重複、MEC(s1cCorrelation 與 GTP tunnel header)、GRE / GTP / VXLAN 關聯、coreSession,重開機後再量;其餘維持出廠。
- 「1 進 1 出」一個產生器、一條鏈;「2 進 2 出」兩個產生器、兩條鏈(10G 的兩條線各自雙向使用)。HL1 只有一個資料埠,「1 進 1 出」是同一個 100G 埠進、同一個埠出,產生器放在 Q16 的 V13 上,分別用 1、2、4 個。

## 接線

| 被測設備 | 產生流量的設備 | 進 | 出 |
|---|---|---|---|
| G8S(1G 埠) | T12S | T12S P6 → G8S P2;2 進 2 出再加 T12S P5 → G8S P6 | G8S P3 → T12S P4;G8S P7 → T12S P7 |
| T12S(10G 埠) | Q16 | Q16 V7 → T12S P1;2 進 2 出再加 Q16 V6 → T12S P0;4 進 4 出再加 Q16 V4 → T12S P2、Q16 V5 → T12S P3 | T12S P0 → Q16 V6;T12S P1 → Q16 V7;T12S P3 → Q16 V5;T12S P2 → Q16 V4 |
| Q16(10G cage) | T12S(每埠兩個到四個產生器核心) | T12S P1 → Q16 V7;2 進 2 出再加 T12S P0 → Q16 V6;4 進 4 出再加 T12S P2 → Q16 V4、T12S P3 → Q16 V5 | Q16 V6 → T12S P0;Q16 V7 → T12S P1;Q16 V5 → T12S P3;Q16 V4 → T12S P2 |

- 1G 埠 64 bytes 的線速是 1.488 Mpps,10G 是 14.88 Mpps,100G 是 148.8 Mpps。
- **G8S**:開 flow 約 0.4 Mpps,是整台引擎的上限而不是單一埠的,2 進 2 出合計反而略低(多一個埠的收發成本);關掉 flow 表與 L7 解析等之後約兩倍。灌到線速時它仍能轉送約 0.5 / 1.06 Mpps,其餘在進埠丟棄,出埠不會掉。
- **T12S**:開 flow 約 3 Mpps,1 進 1 出、2 進 2 出、4 進 4 出都一樣,是整台的上限;關 flow 6.2–6.3 Mpps,也不隨埠數變。
- **Q16**:開 flow 15–16 Mpps(2 進 2 出與 4 進 4 出一樣);關 flow **27 Mpps 無漏失**(4 進 4 出,十二顆 T12S 產生器核心灌 37 Mpps 時轉送 34.5,其餘記在上行埠 P0–P2 的 inDrops;四個 10G 埠的 64 bytes 線速是 59.5 Mpps,27 Mpps 約 45%)。
- **HL1**(一個 100G 埠、8 核心，7 個工作核心)：開 flow 約 **6.0 Mpps** 無漏失(2 個與 4 個產生器都是，整台引擎的上限；1 個產生器時先到頂的是產生器，4.2 Mpps 0 掉包)，關 flow **11.4 Mpps**(4 個產生器；1 個、2 個產生器分別送 4.3、9.8 Mpps 都 0 掉包，是產生器的上限)；灌滿 17.5–18 Mpps 時分別轉送 6.6 與 11.9 Mpps，其餘在進埠丟棄。上限在引擎，不在 100G 埠(100G 線速 148.8 Mpps)。HL1 的 8 顆核心裡 7 顆是引擎的工作核心，網頁服務、SNMP、更新程式與所有中斷都放在 CPU 0(韌體 7.6.261116 起)，不借用工作核心的時間——否則接收佇列會滿、網卡丟掉的封包不計數。
- **HL1 灌滿時仍有一部分掉包不計數**:灌到 18 Mpps 時,inDrops 記了每秒約 600 萬至 1,200 萬個,另外每秒還有約 25 至 43 萬個收進來卻沒送出、也沒記成 drop——核心全部 100% 時接收佇列一樣會滿。所以看 HL1 有沒有掉包,除了 inDrops 也要比對進出的差;本頁對 HL1 的「通過」就是這樣判的(見測試方式),兩者超過約 5 毫秒的流量即算掉包。**引擎 2.9.53 起這種漏失留有痕跡**:工作核心每 64 次收滿一批就問網卡佇列裡還排著多少,超過四分之三(16,384 格的 12,288)就在該埠的 `inQueueFull` 記一次、並在紀錄裡每分鐘最多寫一行(`receive queue over 12288 frames waiting (P0 queue 5 x11 ...) (core 6)`);網頁的告警「接收佇列滿」(pywww 1.47.8)看這個計數,10 秒內有增加就發、最後一次增加 60 秒後解除。
- **Q16 重測(2026-11-16，韌體 7.6.261116)**:用 HL1 的嚴格判定(進出差超過 5 毫秒的流量就算掉包)再量一次,Q16 **沒有**不計數的漏失——每個速率進出都只差幾十個封包,掉的都記在上行埠 P0–P2,一分鐘掉 1–2 個就是失敗點。開 flow 約 15 Mpps、關 flow 約 26 Mpps，和 11-09 用四對線量到的一致，上限在引擎。這次 Q16 的 V5 槽沒有模組,所以只用三對 10G 線(V7、V6、V4),第三對同一埠進出;三對和之前四對的數字一致。
- **Q16 的 100G 單埠**:HL1 當產生器(P0 100G → Q16 V13,四個 25G 模組綁成的 100G 埠),Q16 從 V13 收、送到沒模組的 V5(交換器端丟棄,引擎的送出計數照算),所以沒有回流進 HL1。關 flow **23.65 Mpps**,比三、四個 10G 埠的 26.4–27.1 低約 10%;開 flow 6 個產生器(629 萬 flow,表的 74%)**15.29**,和多埠的 15.7 相當;4 個產生器只有 419 萬 flow(表的 50%),所以 18.44 偏高,是 flow 表較空的緣故,不是埠數。
- **flow 表的使用量會影響開 flow 的數字**,所以本頁以表的 75% 為準。同一台 T12S 開 flow:flow 數 6.5 萬(表 3%)時 1 進 1 出送 4.26 Mpps 不掉包、2 進 2 出 3.98;表 75% 時 2.97 / 2.94;表 87% 時 2.73。G8S:6.5 萬 flow 0.52 / 0.49,75% 0.43 / 0.40,90% 0.35 / 0.29。
- **Q16 的丟包記在引擎的上行埠。** 開 flow 灌到 26.9 Mpps 時,V 埠的進出仍然相等(17.8 = 17.8)、V 埠 inDrops 0,被丟掉的 5.4 億個封包記在 P0–P2(cage 經交換器進引擎的 50G 埠)的 inDrops;看 Q16 有沒有掉包要看 P0–P2。
- CPU 一欄是系統狀態頁的數字;未飽和時可以用它估計還有多少餘裕,到 100% 就是掉包的前一步。HL1 的 core 1 例外:它分到的封包比其他核心多 11%(RSS 分配表 64 格除以 7 個佇列,佇列 0 拿 10 格、其餘 9 格),每次輪詢都有封包、從不休息,所以 1 個產生器時就顯示 99%,其他核心 65–78%;它處理得來,掉包時它反而是最沒事的一顆。
