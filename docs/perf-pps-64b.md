# 64 bytes 封包的每秒轉送量(pps)

最小封包下,一台設備每秒能**不漏任何一個封包**地轉送多少個?本頁是 G8S、T12S、Q16 三個機型在「開 flow 表(出廠預設)」與「關 flow 表(最佳化)」兩種設定下量到的結果(2026-11-06 與 11-09;G8S、T12S 韌體 6.6.261104,Q16 7.6.261106)。每秒封包數是小封包流量的瓶頸:同樣的 pps,封包越大吞吐量越高,所以把 64 bytes 的 pps 乘上實際流量的平均封包大小,就是該設備在那種流量下的上限(例如 0.92 Mpps × 600 bytes ≈ 4.4 Gbit/s)。

## 測試方式

- **被測設備不自己產生流量。** 流量由另一台 GRISM 的 traffic-gen 輸入送出,經實體線進入被測設備;被測設備用一條鏈(一個 `ip.src == 11.0.0.0/8` 過濾器,全部命中)轉送到另一個埠,再接回產生流量的那台計數。沒有用 LOOP 埠。
- **封包**:UDP,`packet_size` 60,線上含 FCS 剛好 64 bytes(traffic-gen 的 `packet_size` 不含 FCS,填 64 會變成 68 bytes 的封包)。每個產生器以一段連續的來源位址輪流送(`src_ip_min` / `src_ip_max` / `src_ip_inc`),所以每個封包都是不同的 flow。
- **flow 數**:開 flow 表的測試讓所有產生器的來源位址總數約等於 flow 表容量(`flowCacheBaseSize × 16`,DPDK 系列再 × 工作核心數)的 **75%**:G8S 48 萬、T12S 180 萬、Q16 635 萬。太少不行——單一 flow 在 OCTEON 上會被 atomic tag 綁在一顆核心,量到的是一顆核心而不是整台(G8S 單一 flow 只有 0.49 Mpps),flow 數只有幾萬時表幾乎是空的、數字會偏高;太滿也不行,接近滿的表會把數字再壓低(見結果後的說明)。關 flow 表的測試 flow 數無關緊要。
- **速率**:第一輪不限速(灌到線速或產生器的上限),掉包就以 traffic-gen 的 `speed` 二分,每輪暖機 15 秒、取 60 秒視窗,共 7 輪(解析度約 1%)。
- **通過**:60 秒內被測設備**所有埠**的 `inDrops`、`inErrors`、`outDrops` 都是 0(Q16 的 NIC 丟包記在引擎的上行埠 P0–P2,不在 V 埠),而且被測設備出 = 進(容許 0.1 秒流量的差:進是硬體計數、出是各核心的軟體計數加總,不是同一瞬間讀的)。產生器那台收到的(inPackets + inDrops,因為它自己的引擎吃不下回流時會丟在進埠)與送出的差只當作超過 1% 才成立的防呆,防的是沒有人計數的漏失(交換器、線)。
- **開 flow**(出廠預設)= 用「回復原廠設定(保留管理 IP)」還原後的設定,不改任何東西(MEC 機型的 MEC 功能為開)。**關 flow**(最佳化)= 關閉 flow / flowv6 表、L7 解析、tunnel 內層解析、SCTP / TCP / QUIC 重組、IP 分片關聯、去重複、MEC(s1cCorrelation 與 GTP tunnel header)、GRE / GTP / VXLAN 關聯、coreSession,重開機後再量;其餘維持出廠。
- 「1 進 1 出」一個產生器、一條鏈;「2 進 2 出」兩個產生器、兩條鏈(10G 的兩條線各自雙向使用)。

## 接線

| 被測設備 | 產生流量的設備 | 進 | 出 |
|---|---|---|---|
| G8S(1G 埠) | T12S | T12S P6 → G8S P2;2 進 2 出再加 T12S P5 → G8S P6 | G8S P3 → T12S P4;G8S P7 → T12S P7 |
| T12S(10G 埠) | Q16 | Q16 V7 → T12S P1;2 進 2 出再加 Q16 V6 → T12S P0;4 進 4 出再加 Q16 V4 → T12S P2、Q16 V5 → T12S P3 | T12S P0 → Q16 V6;T12S P1 → Q16 V7;T12S P3 → Q16 V5;T12S P2 → Q16 V4 |
| Q16(10G cage) | T12S(每埠兩個到四個產生器核心) | T12S P1 → Q16 V7;2 進 2 出再加 T12S P0 → Q16 V6;4 進 4 出再加 T12S P2 → Q16 V4、T12S P3 → Q16 V5 | Q16 V6 → T12S P0;Q16 V7 → T12S P1;Q16 V5 → T12S P3;Q16 V4 → T12S P2 |

- 1G 埠 64 bytes 的線速是 1.488 Mpps,10G 是 14.88 Mpps。
- **G8S**:開 flow 約 0.4 Mpps,是整台引擎的上限而不是單一埠的,2 進 2 出合計反而略低(多一個埠的收發成本);關掉 flow 表與 L7 解析等之後約兩倍。灌到線速時它仍能轉送約 0.5 / 1.06 Mpps,其餘在進埠丟棄,出埠不會掉。
- **T12S**:開 flow 約 3 Mpps,1 進 1 出、2 進 2 出、4 進 4 出都一樣,是整台的上限;關 flow 6.2–6.3 Mpps,也不隨埠數變。
- **Q16**:開 flow 15–16 Mpps(2 進 2 出與 4 進 4 出一樣);關 flow **27 Mpps 無漏失**(4 進 4 出,十二顆 T12S 產生器核心灌 37 Mpps 時轉送 34.5,其餘記在上行埠 P0–P2 的 inDrops;四個 10G 埠的 64 bytes 線速是 59.5 Mpps,27 Mpps 約 45%)。
- **flow 表的使用量會影響開 flow 的數字**,所以本頁以表的 75% 為準。同一台 T12S 開 flow:flow 數 6.5 萬(表 3%)時 1 進 1 出送 4.26 Mpps 不掉包、2 進 2 出 3.98;表 75% 時 2.97 / 2.94;表 87% 時 2.73。G8S:6.5 萬 flow 0.52 / 0.49,75% 0.43 / 0.40,90% 0.35 / 0.29。
- **Q16 的丟包記在引擎的上行埠。** 開 flow 灌到 26.9 Mpps 時,V 埠的進出仍然相等(17.8 = 17.8)、V 埠 inDrops 0,被丟掉的 5.4 億個封包記在 P0–P2(cage 經交換器進引擎的 50G 埠)的 inDrops;看 Q16 有沒有掉包要看 P0–P2。
- CPU 一欄是系統狀態頁的數字;未飽和時可以用它估計還有多少餘裕,到 100% 就是掉包的前一步。

## 產生器本身的上限

- traffic-gen 一個輸入佔一顆核心。G8S 當產生器每埠只有約 0.33 Mpps,所以不用它產生;T12S 一顆核心在 1G 埠可以送滿線速,在 10G 埠一顆核心約 3.4 至 4.3 Mpps,十二顆核心(四個埠各三個)合計 37 Mpps;Q16 一個 lcore 一個埠 4.3 至 5.2 Mpps(都是 64 bytes)。
- 兩個產生器送同一個埠:MIPS 系列可以(PKO 佇列有鎖,每個輸入一顆核心),DPDK 系列只有在埠有對應核心的 tx queue 時才安全,所以 Q16 當產生器時每埠只用一個輸入。
- `speed` 的意義:每秒封包數 ≈ 131072 × speed ÷ packet_size(64 bytes 時約 2184 × speed);0 = 不限速。
