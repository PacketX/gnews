# 多核心下的 strtok:字串是私有的,狀態卻是共用的

## 現象

在 arm64(DPDK)機種上重播同一個瀏覽器封包檔,絕大多數 TLS ClientHello 的 JA4 都正確,但每次總有約 1%~2% 算錯,而且**每次錯的是不同連線**:

| 正確的 JA4 | 偶爾算出的 JA4 |
|---|---|
| `t13d1517h2_8daaf6152771_cb7bf5808d99` | `t13d0317h2_b0e173700538_cb7bf5808d99` |
| | `t13d1017h2_24938229c549_cb7bf5808d99` |
| | `t13d1507h2_8daaf6152771_43af166abec8` |

錯的地方各不相同:有時 cipher 數量變少、JA4_b 跟著錯,但 JA4_c 正確;有時反過來是擴充欄位數量變少、JA4_c 錯。同一個封包檔在 MIPS 機種上則從不出錯。

「每次錯在不同連線」是關鍵線索:解析邏輯若有錯,同一個封包應該每次都錯在同一處;隨機出錯,代表是**時序**問題。

## 原因

計算 JA4 時,要把 cipher 與擴充欄位清單(如 `4865-4866-4867-...`)拆開、排序、再雜湊。拆字串用的是 C 標準函式 `strtok()`。

被拆的字串本身是每次呼叫各自 `strdup()` 出來的副本,看起來是私有的;問題不在字串,而在 `strtok()` **自己記住「目前切到哪裡」的那個指標**。`strtok()` 第一次呼叫傳入字串,之後傳 `NULL` 表示「從上次的位置繼續」,而這個位置存在 libc 內部的一個 static 變數:

```c
char *strtok(char *s, const char *delim)
{
    static char *olds;              /* 整個行程只有一份 */
    return __strtok_r(s, delim, &olds);
}
```

Linux 的 man page 也明確標註 `strtok()` 為 `MT-Unsafe race:strtok`。

- **arm64(DPDK)**:各處理核心是**同一個行程內的多條執行緒**,共用同一個位址空間,也共用同一個 `olds`。
- **MIPS(OCTEON)**:每個核心是**獨立行程**,各有自己的 `olds`,互不干擾。

「私有」只是邏輯上沒有別人該去用那份副本;實際上同一行程的 heap,每條執行緒都讀寫得到。一旦 `olds` 被別的核心改成指向它自己的副本,這個核心接下來就會去切別人的字串。

## 實際發生的順序

以 `t13d0317h2_…` 為例:

| 時間 | 核心 A(拆 cipher 清單) | 核心 B(另一個 ClientHello) | `olds` 指向 |
|---|---|---|---|
| 1 | `strtok(dupA, "-")` 取得第 1 個 | | dupA |
| 2 | `strtok(NULL, "-")` 第 2 個 | | dupA |
| 3 | `strtok(NULL, "-")` 第 3 個 | | dupA |
| 4 | | `strtok(dupB, "-")` 開始拆 | **dupB** |
| 5 | | 一路拆到 dupB 結尾 | dupB 結尾 |
| 6 | `strtok(NULL, "-")` → 從 dupB 的結尾接續 → 回傳 `NULL` | | |

核心 A 以為清單結束了,只數到 3 個 cipher:JA4_a 成了 `t13d03…`,JA4_b 是只有 3 個 cipher 的雜湊;而擴充欄位是之後才拆、沒被干擾,所以 JA4_c 仍然正確。換成擴充欄位清單被截斷,就是 `t13d1507h2_…` 這一型。也可能反過來,核心 A 接著去拆核心 B 的字串,或在對方的副本中寫入 `\0`,把雙方的結果一起破壞。

兩個核心必須**恰好同時**拆字串才會發生,所以錯誤是隨機的,每次重播落在不同連線。

## 修正

改用可重入的 `strtok_r()`,把位置存在呼叫者自己的變數(在各自的堆疊上),每次呼叫、每個核心各一份:

```c
char *save = NULL;
char *tok = strtok_r(dup, "-", &save);
while (tok) {
    /* ... */
    tok = strtok_r(NULL, "-", &save);
}
```

只呼叫一次、用來截斷字串的 `strtok(s, ":;")` 同樣會寫入共用的 `olds`,可能打斷另一個核心正在進行的拆解,也一併改成不碰共用狀態的寫法:

```c
size_t lead = strspn(s, ":;");
s[lead + strcspn(s + lead, ":;")] = '\0';
```

## 驗證

同一台 arm64 機種、同一個封包檔、同一份程式碼,只差這個修正,把設備算出的 JA4 逐筆和獨立的參考實作比對:

| 韌體 | 重播次數 | TCP ClientHello | 算錯 |
|---|---|---|---|
| 未修正 | 2 | 546 | 3(每次不同連線) |
| 修正後 | 5 | 1365 | 0 |

## 結論

- 會被多核心同時執行的程式碼,不能使用帶有隱藏 static 狀態的函式。除了 `strtok()`,常見的還有 `strerror()`、`localtime()`、`gmtime()`、`asctime()`、`ctime()`、`rand()`、`inet_ntoa()` 等,應改用 `_r` 版本(`strtok_r`、`localtime_r`、`strerror_r`…)或不依賴共用狀態的寫法。
- 「資料是私有的」不等於「執行緒安全」:要看的是函式內部有沒有共用狀態。
- 同一份程式碼在「一核心一行程」的架構上正確,換到「一核心一執行緒」可能就會出錯,移植時要特別檢查。
- 結果隨機、每次錯在不同地方,通常就是競爭條件。用固定的輸入重複執行並和參考實作逐筆比對,是最快的確認方法。
