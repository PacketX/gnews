# 讓自動化與 AI 管理 GRISM:權杖、驗證、推演、確認式提交、能力與事件

## 為什麼

AI 或自動化程式管機房時不看網頁,它看 API 和事件。從它的角度,GRISM 是網路裡的眼睛和手:看得到每一個封包(JA4、SNI、DNS、GTP、MEC session),也能即時改分流、側錄、繞路。缺的不是「能不能被程式操作」——每個操作早就有 API——而是三件讓程式**敢**操作的事:

1. 一個不是人的身分,權限有邊界、做了什麼有紀錄。
2. 改錯之前能知道、改錯之後能自己復原。
3. 不用輪詢就知道裝置發生了什麼,而且先知道這台裝置能做什麼。

2026-10-16 起(pywww 1.47.0 / 1.45.0、Studio 2.261.0)這三件都在。端點與參數的完整表在〈[Web API](tech-web-api.md)〉的「自動化」一節,這裡說的是設計。

## 1. API 權杖:程式的身分

設定 → 登入驗證 → API 權杖。建立時指定名稱、等級、有效天數、允許的來源位址;權杖 `gpx_…` 只顯示一次,裝置只保存它的 SHA-256。之後每個請求帶 `Authorization: Bearer <權杖>`,不需要登入也沒有 session 過期的問題。

幾個刻意的限制:

- **權杖的等級最高是「設定」,不能是「管理」。** 韌體更新、帳號、管理 IP、備份還原這些留給人。
- 可限制來源:列了位址或網段,從別處送來就當作沒有權杖。
- 一個不對的權杖(未知、過期、來源不符)回 404,和沒登入一樣,**不會**退回去用同一個請求可能帶著的 cookie。
- 系統紀錄與事件裡,它做的每件事都記成 `token:<名稱>`,和人的操作分得開。

## 2. 改之前先知道,改之後能復原

**validate** — 把 `<run>` 送去檢查、不套用:XML 是否完整、id 是否重複、鏈結引用的篩選器與輸出是否存在、埠是否是這台的、每個 `<find>` 的欄位名稱是否在這版韌體的目錄裡。最後一項以前沒有辦法事先知道:韌體遇到不認得的欄位會**默默丟掉**那個條件,留下一個比寫的寬鬆的篩選器。目錄現在隨韌體出廠(`etc/fields.json`,從引擎的 `fc.c` 產生),驗證對的就是引擎真的接受的那份。

**trace** — 給一個入口埠和封包的描述(來源/目的 IP、協定、埠號、VLAN、MAC、隧道種類),裝置從設定推演它會走哪條鏈結、哪個篩選器命中、從哪裡出去。能由參數判定的篩選器直接判定;判定不了的(例如要看連線狀態、heartbeat、對應表或 L7 內容的)把路徑分成兩條,各自記下假設了什麼。`live=1` 會附上每個篩選器目前的命中數,讓程式對照「推演說會命中」和「實際有沒有在命中」。也可以 POST 一份候選設定來推演,所以「改了之後 X 會不會還走原路」在提交前就能問。

要老實說的是:這是對 `run.xml` 的靜態分析,不是引擎跑一個封包。它回答的是結構問題,不是深度解析的結果。

**確認式提交(commit-confirm)** — `submitxml` 多一個 `confirm=秒數`。裝置先把執行中的檔案留一份,再套用新的;時限內沒收到 `confirm_submit`,自動換回舊的。路由器世界的 commit-confirmed 就是為「把自己鎖在外面」設計的;分流器一樣會,改錯一條鏈結可能讓管理網路也不通。同一時間只允許一個待確認的提交;`rollback_submit` 可以不等時限立即換回。待確認的狀態存在裝置上(不是記憶體),所以 web 服務重啟也不會忘記要還原。Studio 的匯出頁有同樣的選項,也會顯示任何人(包括程式)提交後等待確認的橫幅,可以按確認或立即還原。

## 3. 先知道能做什麼,事情發生時被告知

**get_capabilities** — 一次回答「這台是什麼」:機型、韌體與引擎版本、產品線、每個埠(含哪些是 LOOP)、管理位址、儲存空間、可用的篩選欄位、各表的大小與功能開關、記憶體、bypass 配對、以及這些自動化呼叫的對照表。程式接上一台沒見過的裝置,讀這一筆就知道該怎麼寫設定。

**事件** — 四種:`alert`(告警觸發與解除)、`config`(提交、暫時設定、configSet、確認、還原)、`engine`(封包引擎的行程改變 = 重啟或當機)、`auth`(權杖建立與刪除、登入失敗)。兩種拿法:

- **Webhook**(設定 → 告警 → Webhook,最多 8 個):事件發生時以 JSON POST 到網址,標頭 `X-Grism-Event` 是種類,設了密鑰就有 `X-Grism-Signature: sha256=<HMAC>` 可驗。送不到只在系統紀錄寫一次,五分鐘內不重複。
- **`get_events?since=<id>`**:裝置保留最近 500 筆,錯過推送的程式用上次的 `last_id` 補。

MEC 的 UE 上線、換手等事件不在這條匯流排上——那一類的量大,仍由引擎的 `mec` 型 syslog 目標送出。

## 要不要在設備上裝 AI agent?

不建議在設備上跑推理。MIPS 機種給 Linux 的只有約 530 MB,核心是給封包的;arm64 機種記憶體多,但 CPU 一樣。推理放在設備外、一個 agent 管幾十台,也才有全網視角。設備上該有的是確定性的自動化(告警規則、watcher、閒置清除),加上這篇的介面,讓外面的 agent 用得安全。離線或機密場域若真的需要本機 agent,應是資源上限固定、不在封包路徑、有 kill switch 的 sidecar,而且變更照樣走確認式提交——這是第二階段的事。

## 一個 agent 的典型流程

```
get_capabilities      → 這台有哪些埠、欄位、功能
get_events / webhook  → 被告知告警、引擎重啟、設定變更
validate(候選設定)    → 問題為零再往下
trace(候選設定, 封包) → 關鍵流量的路徑沒變
submitxml?confirm=60  → 套用
觀察命中數、連通性    → confirm_submit,否則什麼都不做、60 秒後自動還原
```

每一步都有紀錄:誰(哪個權杖)、何時、做了什麼,以及裝置自己做的還原。
